# Fast-Pass Pilot Phase 1 Results — Replay Eval, July 2026

Deliverable of Phase 1 in [narration-fastpass-pilot-plan.md](narration-fastpass-pilot-plan.md):
the offline replay eval measuring whether `gpt-realtime-2.1` (conversation
mode, function calling) is reliable enough to revive live fast-pass event
extraction. Run 2026-07-21 on branch `fastpass-eval`.

**Harness**: `ultistats_server/tests/narration/runner.py` gained
`stream_audio_for_events()` (conversation-mode replay: semantic VAD
`eagerness: low`, `far_field` noise reduction, parallel input transcription,
no-call-default instructions, required `confidence` field, `retract_event`
tool, net-event scoring after retractions, production-mirroring player-name
resolution + unresolvable-event drops). Driver:
`fastpass_eval.py` (`--baseline` runs the production transcription +
slow-pass path on identical audio). New confabulation probes:
`023_noise_only_wind`, `024_noise_only_sideline` (real speech, zero narrated
actions), `025_narration_over_crowd` (002's narration ~4 dB over a crowd
bed), generated by `tools/generate_noise_audio.py`.

## Headline numbers (full suite, 22 event scenarios, 54 expected events)

| | precision | recall | F1 | noise-only confabs |
|---|---|---|---|---|
| Fast pass (`gpt-realtime-2.1`) | **0.949** | 0.685 | 0.796 | **0 (across 5 runs × 2 scenarios)** |
| Slow pass baseline (Haiku 4.5, production model) | 0.980 | 0.907 | 0.942 | 0 |

- **Confabulation (the gate metric): passed.** Zero events emitted on pure
  wind and on sideline chatter (cheering, "nice throw!", disc talk) in every
  run. The no-call-default prompt works: on chatter the model transcribes
  everything and calls nothing.
- **Precision on real/degraded audio:** `022_live_field_point` (the only
  real outdoor recording) P=1.00 R=0.86 on the final run (P=0.71 on an
  earlier run — variance, see below); `025_narration_over_crowd` P=1.00 in
  all 4 runs, recall 0.33–1.00 run-dependent.
- **Recall lags badly (expected):** 0.69 vs 0.91. Dominant failure: on long
  multi-event utterances the model logs the first 1–2 events, emits planning
  text ("I'll log the remaining pass…"), and never finishes (003, 007, 008,
  014 all lost tail events). Semantic VAD `eagerness: low` makes utterances
  long, which aggravates this.

## Correction handling (scenarios 004\*, 005, 006, 008\*)

Within-utterance corrections work: with `eagerness: low` the model hears the
full utterance before responding and simply emits the corrected version
(004, 005 perfect; 006 perfect in one of two runs). **The retract path does
not work**: `retract_event` was never called in any run. In 006's failing
run the model logged the uncorrected throw ("Score!"), *said in text* it
would update it after the correction, and never did — exactly the
stale-provisional-event UX the pilot plan worries about. The slow pass would
clean it up, but it would be on the coach's screen until then.

## Research questions answered

- **`strict: true` on GA realtime tools: rejected** —
  `unknown_parameter: 'session.tools[0].strict'` on `session.update`. The
  harness falls back to non-strict automatically. Consequence: malformed
  calls happen (`record_throw {}`, empty receivers) and must be dropped
  client-side (production's appliers already did).
- **Run-to-run variance is large.** Same audio, same config: 020 scored
  0.00 then 1.00; 013 0.00 then 1.00; 006 1.00 then 0.00; 008 0.40 then
  0.25. Single-run scores on this model are not trustworthy; any future
  config comparison needs ≥3 runs per scenario.
- **Transcript-vs-events divergence is real** (as the research doc's fine
  print warned): in 022 the parallel transcript garbled names the function
  calls got right, and vice versa.

## Coverage gaps

- The hand-recorded outdoor scenarios the plan pointed at
  (`004b_yoyo…`, `008b…`, `015b…`, `019b…`, `021…`) have fixtures but **no
  committed audio** — they were never recorded (or the files were lost).
  The outdoor evidence is one 65s recording (022) plus the synthetic crowd
  overlay (025). More real recordings remain the biggest lever for
  confidence here.
- Cost per full-suite fast-pass run: well under $1 (≈3.5 min of audio).

## Verdict vs the plan's acceptance bar

- Zero noise-only confabulations across 3 runs: **met** (0 across 5 runs).
- Outdoor precision within a few points of the slow pass: **met on the
  available audio** (1.00 vs 1.00 on 022/025 final runs) — but the evidence
  base is thin (one real recording) and variance is high.
- Not in the bar but material: recall 0.69, the dead retract path, and
  model text-chatter instead of tool calls are all live-UX concerns for
  Phase 2 (provisional events that are missing or stale until the slow pass
  lands).
